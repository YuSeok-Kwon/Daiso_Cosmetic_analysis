다이소 뷰티 프로젝트의 데이터 수집부터 분석용 테이블 생성까지의 전체 흐름을 문서화한다.

- **최종 수정일**: 2026-02-22
- **소스 코드**: `05_src/04_pipeline/`
- **실행 명령어**: `python 05_src/04_pipeline/run_pipeline.py`

## Step 1: 데이터 수집 (크롤링)

### 1.1 크롤링 대상

다이소몰 뷰티 카테고리의 전체 상품 페이지를 Selenium으로 크롤링한다.

| 항목 | 내용 |
|------|------|
| 소스 | 다이소몰 (daisomall.co.kr) |
| 범위 | 뷰티/위생 > 6개 중분류, 33개 소분류 |
| 수집 데이터 | 제품 정보, 리뷰, 전성분 |
| 기술 | Selenium + Clova OCR + EasyOCR + OpenCV |
| 소스 코드 | `05_src/01_crawling/daiso_beauty_crawler.py` |

### 1.2 수집 데이터 구조

크롤러는 3개의 raw CSV를 생성한다.

#### products_all_YYYYMMDD.csv

| 컬럼 | 설명 |
|------|------|
| `product_code` | 제품 고유 코드 (URL의 pdNo) |
| `category_home` | 1차 분류 ("뷰티/위생") |
| `category_1` | 중분류 (스킨케어, 메이크업 등) |
| `category_2` | 소분류 (로션, 에센스, 립스틱 등) |
| `brand` | 브랜드명 |
| `name` | 제품명 |
| `price` | 판매가 (원) |
| `country` | 제조국 |
| `likes` | 좋아요 수 |
| `shares` | 공유 수 |
| `url` | 제품 페이지 URL |

#### reviews_all_YYYYMMDD.csv

| 컬럼 | 설명 |
|------|------|
| `product_code` | 제품 코드 |
| `date` | 리뷰 작성일 (YYYY.MM.DD) |
| `user_masked` | 마스킹된 사용자 ID (앞 3글자 + *) |
| `user` | 내부 식별자 (user_NNNN) |
| `rating` | 별점 (1~5) |
| `text` | 리뷰 본문 |
| `image_count` | 첨부 이미지 수 |

#### ingredients_all_YYYYMMDD.csv

| 컬럼 | 설명 |
|------|------|
| `product_id` | 제품 코드 |
| `name` | 제품명 |
| `ingredient` | 성분명 (정규화 완료) |

### 1.3 성분 추출 방식

성분 데이터는 다중 소스 교차 검증 방식으로 추출한다.

```
[제품 상세 페이지]
    │
    ├── (1) ALT 텍스트 추출
    │       이미지 alt 속성에서 "전성분" 섹션 인식 → 성분명 파싱
    │
    ├── (2) OCR 교차 검증
    │       ├── 멀티 이미지 → 마지막 2장에 Clova OCR
    │       └── 싱글 이미지 → Bottom-Up 3920px 크롭 후 OCR
    │
    └── (3) 신뢰도 기반 필터링
            ├── confidence >= 0.5 필터
            ├── 다중 소스 발견 시 +5% 가산
            └── normalize_ingredient_name()으로 정규화
                (OCR 오인식 교정: 소톱→소듐, 글라이골→글라이콜 등)
```

### 1.4 증분 크롤링

매번 전체를 크롤링하지 않고, **신규 제품만 전체 수집 / 기존 제품은 새 리뷰만 수집**하는 증분 모드를 지원한다.

#### 동작 흐름

```
카테고리 페이지에서 product_code 목록 수집
    │
    ├── crawl_history.json에 없음 (신규 제품)
    │     └── 전체 크롤링 (제품 정보 + 리뷰 + 성분)
    │
    └── crawl_history.json에 있음 (기존 제품)
          └── cutoff = last_review_date
          └── 리뷰만 수집 (cutoff 이후 새 리뷰, 성분 생략)
                └── 리뷰가 날짜 역순이므로 cutoff 도달 시 조기 종료
```

#### 이력 관리 (CrawlHistory)

`05_src/01_crawling/crawl_history.py`

```json
{
  "last_updated": "2026-02-19",
  "products": {
    "1056665": {"last_crawled": "2026-02-19", "last_review_date": "2026-02-15"},
    "1048275": {"last_crawled": "2026-02-19", "last_review_date": "2026-02-10"}
  }
}
```

| 메서드 | 설명 |
|--------|------|
| `is_new_product(code)` | 이력에 없으면 True |
| `get_last_review_date(code)` | 다음 증분의 cutoff 날짜 |
| `update_product(code, date)` | 크롤링 후 이력 갱신 |
| `save()` | 임시파일 → `os.replace()` 원자적 교체 (비정상 종료 대응) |
| `from_existing_csv(path, reviews_csv)` | 첫 실행 시 bootstrapping |

#### Bootstrapping (첫 실행)

```
crawl_history.json 존재? ──Yes──→ 그대로 로드
        │No
reviews_core.csv 존재? ──Yes──→ product_code별 max(review_date) 추출 → 이력 초기화
        │No                       → 기존 제품은 리뷰만 업데이트
빈 이력 생성 → 모든 제품 신규 → 풀 크롤링과 동일
```

#### 효율성 비교

| 항목 | 풀 크롤링 | 증분 크롤링 |
|------|-----------|-------------|
| 제품 정보 | 전체 (~670개) | 신규만 (~10~30개/월) |
| 성분 OCR | 전체 | 신규만 |
| 리뷰 수집 | 전체 (~30만건) | cutoff 이후만 (~1~3만건/월) |
| 예상 소요 시간 | 8~12시간 | 1~3시간 |

### 1.5 카테고리 관리

`config.yaml`에서 크롤링 대상 카테고리를 선택할 수 있다.

```yaml
active_categories:
  스킨케어:
    - all                # 중분류 전체 소분류
  메이크업:
    - 베이스메이크업     # 특정 소분류만
    - 립메이크업
  # 네일용품:            # 키 제거 → 비활성화
```

| 설정 | 동작 |
|------|------|
| `- all` | 중분류의 모든 소분류 활성화 |
| 개별 소분류 | 해당 소분류만 크롤링 |
| 중분류 키 없음 | 해당 중분류 비활성화 |
| `active_categories` 없음 | 전체 카테고리 (6중분류 33소분류) |

`_parse_active_categories()`는 `DAISO_BEAUTY_CATEGORIES`와 교차 검증하여 잘못된 이름에 대해 경고를 출력한다.

## Step 2: 데이터 변환 (Raw → ERD 13개 테이블)

`transformer.py`의 `CrawlerToERDTransformer`가 3개 raw CSV를 정규화된 13개 ERD 테이블로 변환한다.

### 2.1 변환 순서

FK 의존성을 반영한 순서로 변환한다.

```
[참조 테이블 먼저]                          [의존 테이블 나중에]
 1. brand           ─┐
 2. manufacturer     │── 마스터
 3. ingredients_dic  │
 4. promotions      ─┘
                          5. products_core      ─── brand, manufacturer 참조
                          6. products_category   ─── products_core 참조
                          7. products_ingredients ── products_core, ingredients_dic 참조
                          8. functional          ─── products_core 참조
                          9. reviews_core        ─── products_core, users, promotions 참조
                              + reviews_text
                         10. products_stats      ─── products_core + reviews_core 파생
                         11. users_profile       ─── reviews_core 파생
                         12. users_repurchase    ─── reviews_core + products 파생
```

### 2.2 테이블별 변환 로직

#### 마스터 테이블 (크롤러 → ID 할당)

| 테이블 | 소스 | 변환 로직 |
|--------|------|-----------|
| **brand** | `products_raw.brand` unique | 기존 brand_id 매핑 보존 + 신규 브랜드에 ID 할당 |
| **manufacturer** | 기존 데이터 유지 | 크롤러 미수집 → **식약처(MFDS) API** 필요 |
| **ingredients_dic** | `ingredients_raw.ingredient` unique | ID 할당 + 기존 `ingredient_type`, `application_role` 보존 |
| **promotions** | 수동 관리 CSV | 입력 그대로 통과 (없으면 기존 final/ 데이터 유지) |

#### 제품 테이블

| 테이블 | 소스 | 변환 로직 |
|--------|------|-----------|
| **products_core** | `products_raw` | product_code, brand_id, manufacturer_id, name, price, country |
| **products_category** | `products_raw` | product_code, category_1, category_2 |
| **products_ingredients** | `ingredients_raw` | product_code × ingredient_id N:M 매핑 |
| **functional** | 기존 데이터 유지 | 크롤러 미수집 → **식약처(MFDS) API** 필요 |

#### 리뷰·유저 테이블

| 테이블 | 소스 | 변환 로직 |
|--------|------|-----------|
| **reviews_core** | `reviews_raw` | review_id 생성, user_id 할당, is_reorder 파생, promotion_id 매칭 |
| **reviews_text** | `reviews_raw` | review_id, text, review_length 파생 |
| **users_profile** | reviews_core 파생 | activity_level, rating_tendency, review_tenure 계산 |
| **users_repurchase** | reviews + products 파생 | 카테고리/브랜드 재구매 횟수 집계 |

#### 파생변수 테이블

| 테이블 | 소스 | 변환 로직 |
|--------|------|-----------|
| **products_stats** | products + reviews 파생 | engagement_score, cp_index, review_density 계산 |

### 2.3 ID 할당 및 유지 전략

파이프라인은 매 실행마다 기존 `final/` 디렉토리의 CSV를 로드하여 **이전에 할당된 ID를 보존**한다.

```
기존 final/brand.csv → brand_id 매핑 보존
    │
    ├── "어피치" → brand_id=1 (기존 유지)
    ├── "해서린" → brand_id=2 (기존 유지)
    └── "새브랜드X" → brand_id=201 (max_id+1로 신규 할당)
```

동일한 방식이 `ingredients_dic`, `users_profile`, `reviews_core`에도 적용된다.

### 2.4 is_reorder 파생

리뷰 텍스트가 "재구매"로 시작하면 `is_reorder=True`로 판정한다.

```python
df["is_reorder"] = df["text"].fillna("").str.startswith("재구매")
```

- 전체 리뷰 중 재구매 비율: 약 29.99% (98,007건)
- 다이소몰의 "재구매" 마킹 기능을 활용한 판정

### 2.5 프로모션 매칭 (Review ↔ Promotion)

`assign_promotion.py`가 리뷰를 프로모션에 자동 매칭한다.

#### promotions.csv 구조 (수동 관리)

```csv
promotion_id,start_date,end_date,description,brand_id,event_type
1,2025-06-01,2025-06-30,다이소데이 뷰티,95,구매이벤트
2,2025-07-10,2025-07-25,해서린 여름 리뷰,23,리뷰이벤트
```

- `brand_id=95` (ALL): 전체 브랜드 대상 프로모션
- `event_type`: `구매이벤트` / `리뷰이벤트`
- **이 파일만 직접 편집**하면 다음 파이프라인 실행 시 자동 반영

#### 매칭 로직

```
리뷰 (review_date, product_code)
    │
    ├── product_code → brand_id 매핑 (products_core 조인)
    │
    └── 프로모션 룩업
          ├── 조건 1: brand_id 일치 (또는 brand_id=95 ALL)
          ├── 조건 2: review_date가 프로모션 기간 ± 7일 버퍼 내
          │
          └── 복수 매칭 시 우선순위:
                ① 브랜드 특정 > ALL (전체 대상)
                ② 프로모션 중심일에 가까운 것
                ③ promotion_id가 작은 것

미매칭 → promotion_id = 0
```

#### 버퍼 기간 (±7일)

프로모션 시작/종료일 전후 7일을 포함하여 매칭한다. 이는 프로모션 직전 기대 구매와 종료 직후 지연 리뷰를 포괄하기 위함이다.

```
  ← 7일 →  ← 프로모션 기간 →  ← 7일 →
  |--------|================|--------|
  buffer    start      end    buffer
```

### 2.6 파생변수 계산

`derived_features.py`에서 3개 테이블의 파생변수를 계산한다.

#### products_stats

| 변수 | 계산식 | 설명 |
|------|--------|------|
| `review_count` | `COUNT(reviews per product)` | 제품별 리뷰 수 |
| `engagement_score` | `0.15×likes + 0.30×shares + 0.55×review_count` | 가중 인기도 (변동계수 기반 가중치) |
| `cp_index` | `(engagement_score / price) × 1000` | 가성비 지표 |
| `review_density` | `review_count / (last_review - first_review).days` | 리뷰 밀도 (일평균 리뷰 유입) |

#### users_profile

| 변수 | 계산식 | 설명 |
|------|--------|------|
| `user_total_reviews` | `COUNT(reviews per user)` | 유저별 리뷰 수 |
| `user_activity_level` | Newbie(1건) / Junior(2~5) / Regular(6~20) / VIP(21+) | 활동 등급 |
| `user_avg_rating_reorder` | 재구매 리뷰 평균 평점 | 재구매 시 만족도 |
| `user_rating_tendency` | No Reorder / Critical / Balanced / Mostly Positive / Always Positive | 평점 성향 |
| `review_tenure` | `(last_review - first_review).days` | 리뷰 활동 기간 |

#### users_repurchase

| 변수 | 계산식 | 설명 |
|------|--------|------|
| `user_category_repurchase` | 동일 category_1에 2회 이상 구매한 리뷰 총합 | 카테고리 재구매 |
| `user_brand_repurchase` | 동일 brand_id에 2회 이상 구매한 리뷰 총합 | 브랜드 재구매 |

### 2.7 외부 데이터 소스 (크롤러 미수집)

3개 테이블은 크롤러가 아닌 외부 소스에서 데이터를 가져온다. 파이프라인은 기존 `final/` 데이터를 유지하는 방식으로 처리한다.

| 테이블 | 외부 소스 | 보강 컬럼 | 스크립트 |
|--------|----------|-----------|----------|
| **manufacturer** | 식약처(MFDS) API | ENTP_NAME (제조사명) | `05_src/03_mfds_api/` |
| **functional** | 식약처(MFDS) API | ITEM_PH, is_whitening, is_wrinkle_reduction, is_sunscreen, is_acne | `05_src/03_mfds_api/functional_cosmetics.py` |
| **ingredients_dic** | 식약처 + 수동 | ingredient_type, allergic, effect | 별도 enrichment |

식약처 API 파이프라인의 상세 흐름은 `07_docs/ingredients/MFDS_API_파이프라인.md` 참조.

### 3.2 저장 형식

| Parquet | 압축 | 빅데이터 처리, BigQuery 업로드 |

### 3.3 BigQuery 업로드 (선택)

`--upload-bq` 옵션 또는 `config.yaml`의 `bigquery.enabled: true` 설정 시 13개 테이블을 BigQuery에 업로드한다.

## CLI 사용법

```bash
# 증분 크롤링 (기본) → 변환 → 저장
python 05_src/04_pipeline/run_pipeline.py

# 강제 풀 크롤링
python 05_src/04_pipeline/run_pipeline.py --full

# 크롤링 건너뛰고 기존 CSV로 변환만
python 05_src/04_pipeline/run_pipeline.py --skip-crawl \
    --products data/products.csv \
    --reviews data/reviews.csv \
    --ingredients data/ingredients.csv

# BigQuery 업로드 포함
python 05_src/04_pipeline/run_pipeline.py --upload-bq

# 로컬 저장만
python 05_src/04_pipeline/run_pipeline.py --local-only
```

| 옵션 | 설명 |
|------|------|
| `--full` | 이력 무시, 전체 재크롤링 |
| `--skip-crawl` | 크롤링 건너뛰기 (기존 CSV 재사용) |
| `--products`, `--reviews`, `--ingredients` | 기존 raw CSV 경로 |
| `--upload-bq` | BigQuery 업로드 포함 |
| `--local-only` | 로컬 저장만 (BQ 비활성) |
| `--final-dir` | 기존 final/ 디렉토리 경로 (ID 유지용) |
